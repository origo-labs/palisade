01 — verdicts

Four answers, and one of them is not a stricter no.

A supervisor that returns a binary result cannot tell you the difference between the work is wrong and the check could not run. That distinction was learned the expensive way: a predecessor verifier that failed to start, and one whose tests failed, were indistinguishable to its caller — which confounded every measurement made through it.

accept0

Every enabled gate ran and passed.

block1

At least one error-severity finding, each with evidence.

escalate3

Something wants a human, and nothing is blocking.

error2

No verdict was reached. A gate could not run.

Code 2 is not a stricter code 1. A gate that could not run has not passed, and a contract that cannot be read has not been violated. Every one of the two hundred and fifty-three replays returned error zero times — not because the code is perfect, but because the two failure modes are no longer the same thing.

02 — gates

What it can check, and what it will not pretend to.

Ten gates run. Two are in the vocabulary and deliberately refuse to run, so a contract that asks for them fails loudly instead of going quietly green — which is the failure mode this whole design exists to prevent.

gateasksstate
dependency_surface_unchanged did a production dependency, feature, or default-features change? runs
tests_not_deleted did a test disappear, or gain #[ignore]? runs
public_api_unchanged did a public item's signature change or vanish? runs
unsafe_surface_unchanged was unsafe surface added? runs
suppressions_not_widened was an #[allow] added, or broadened to a wildcard? runs
paths_unchanged was a frozen path touched? runs
checks_green do fmt, clippy and test pass? runs
external_tool what did a third-party gate say? (slop-gate verified) runs
contract_not_loosened did this diff weaken the contract without saying why? locked
contract_review_stale is the review date still fresh? locked
secret_absent credential-shaped strings in the diff? refuses
judged is this change on-topic for the job? (escalate-only) refuses

Locked means you cannot declare them, and cannot remove them. Both were originally declarable — and a worker deleted the declaration and got accept. A gate that can be switched off by the thing it guards is not a gate.

03 — the gap

The part most tools leave out is the part worth owning.

A contract that checks dependencies and green tests will happily pass a change that is compliant and strategically wrong. That is not a bug in the gates. It is what deterministic means.

So the gap is not an absence — it is a required, dated, owned artefact. Every run prints it. An empty list is a warning, because an empty list is a contract claiming more than it delivers.

This is the difference between a tool you run and a tool you rely on, and it is the one a marketing page has no incentive to advertise.

palisade.toml [judgement] — required 
# The gap. Mandatory, and deliberately not empty.
# These are real things this suite cannot check,
# and a human still has to look at them.
[judgement]
reviewed = "2026-09-30"
not_covered = [
"whether the chosen design is the right one",
"whether error messages are good enough",
"whether an added benchmark is a fair one",
"whether the code is understandable to someone",
  who did not write it",
"whether a test asserts what it claims to assert",
]

# Gates are seeded at warn: this proposes,
# it does not judge.
[[gates]]
id = "no_new_dependencies"
check = "dependency_surface_unchanged"
severity = "warn"

04 — the measurement

The bugs we found by running it, not by reading it.

Four times a correct-looking value produced a confidently wrong answer. A failing gate is noticed. A gate that reports no change because it could not read anything looks exactly like a pass. Every one of these was caught by running the suite against real repositories, and none by reading the code.

accepted→ caught

documented items looked unchanged

A comment stripper matched // inside /// and then hunted for a block-comment close in a line comment, swallowing every documented declaration in a file. The API gate reported no change — correctly, given what it was handed, and completely silently. An empty signature now makes the parser refuse, so the value cannot be constructed at all.

accepted→ caught

a file split looked like mass deletion

A merge where one file became a module moved 17 tests between files. The gate saw one file lose its tests and reported all 17 deleted. Verified: 17 before, 17 after, none deleted. A test's identity is now its module path, and not its file.

accepted→ caught

a third-party tool's findings were discarded

slop-gate reports its findings and exits 0 at warning level. Branching on the exit code alone dropped every one. The first live run absorbed zero findings from a tool that had one, and printed pass.

What the corpus did and did not show

  • 253 merges, ten repositories, generated contracts. Zero Untrustworthy. Zero blocking-severity false positives.
  • One real substantive finding: a merge that silently dropped four tests — in a repository whose CONTRIBUTING.md says every PR must pass its checks.
  • We judged our own findings. The corpus has one author, who is also the person choosing the gates.
  • checks_green is unmeasured on anything large. It runs cargo test --workspace; on a 38-member crate that is minutes per merge.
  • No independent false-positive review exists. Whether a maintainer finds these findings tolerable is the one question a corpus cannot answer.

The most valuable thing this beta can report is a gate you switched off. Silence is the failure mode this product is most vulnerable to, and it looks exactly like success.

05 — install

Three commands to a first verdict.

$ cargo install --git https://github.com/mrorigo/palisade palisade-cli
  1. palisade init writes a starting contract. Every gate at warn — it proposes, it does not judge.
  2. palisade check runs it. Nothing blocks until you promote a gate to error and say why.
  3. Read the not_covered list. That is the part of the job still yours.

CI

- run: cargo install --git https://…/palisade palisade-cli - run: palisade check --format sarif > results.sarif continue-on-error: true # upload even on a block - uses: github/codeql-action/upload-sarif@v3 if: always() with: sarif_file: results.sarif

Findings land in code scanning. The JSON schema keeps acceptance, rule_violations and residual_judgement separate — conflating “breaks a rule” with “should intervene” is what confounded the measurement that motivated this.

Palisade

A supervisor for coding agents that runs a project's declared quality contract, and escalates only what the contract could not cover. Deterministic. No model in the loop. No network at analysis time.
